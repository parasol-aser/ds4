\title{Where the Tokens Go: Decomposing and Closing the Decode Gap for a 27B Hybrid LLM on Apple Silicon}
\author{Anonymous submission}
\date{Draft, September 2026}

\begin{document}
\maketitle

\begin{abstract}
Open-weight models in the 20--30B range now run on personal machines, and
Apple silicon with unified memory holds one in a single address space.
Single-stream decode there is usually called memory-bandwidth bound: every
step reads every active weight, so the step time should be model bytes over
bandwidth. Yet a widely used runner spends 42~ms per decode step on
Qwen3.8-27B in Q4\_K on an M2~Ultra, against about 24~ms to stream the
weights at the best rates this GPU achieves. This paper asks where the rest
goes. We decompose a decode step into weight streaming, matvec kernel
efficiency, per-dispatch overhead and CPU work between tokens, timing each
stage with command-buffer GPU timestamps so that sub-millisecond kernels are
attributed correctly, and find that each of the last three costs milliseconds
at this scale. Inside \ds{}, an open-source model-specific C/Metal engine, we
add the model and pull three levers, each behind a runtime switch: fewer
bytes per token, fewer and better-shaped dispatches, and a shorter CPU path
between tokens. The switches are worth 4.2~ms of a 35.0~ms step; the
resulting engine takes 30.6~ms per forward against llama.cpp's 42.3, with
logits matching llama.cpp at eight decode-step and context-length points.
Two findings reach beyond this engine. A controlled experiment with the same
source checkpoint in Q4\_0 and Q4\_K shows that the block format is worth
8--16\% with simple kernels and 2--3\% once the large matvecs are fused, so
format and kernel design must be judged together. And a 2~ms-per-token cost
hiding in the sampler, an \texttt{isfinite} call left standing under
\texttt{-ffast-math}, shows that the CPU gap between tokens has to be
measured on its own. We report the optimizations that did not help and why,
and release the code, switches, logs and scripts.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Open-weight models in the 20--30B range fit on a laptop or desktop with
64--192~GB of unified memory, and people run them locally for chat, coding
agents and private workloads. On such a machine the question is no longer
whether a model fits but how fast it decodes, and the standard answer is a
roofline argument: a single-stream decode step reads every active weight
matrix once, so the step time is bounded below by model bytes over memory
bandwidth. For Qwen3.8-27B in Q4\_K on an M2~Ultra that is 15.06~GB per step
at a nominal 800~GB/s, or 18.8~ms; using the best streaming rate we measure
for each weight format on this GPU, about 24.3~ms (\S\ref{sec:roofline}).
llama.cpp takes 42.3~ms per decode step (\S\ref{sec:eval}). Roughly 18~ms of
every step is not accounted for by streaming the weights, and this paper is
about where it goes.

That time is hard to see, which is why it persists. A profiler that
synchronizes at stage boundaries pays about 0.16~ms per boundary on this
machine, more than most of the kernels it is trying to measure, so small
kernels vanish into the floor. A system trace reports the GPU 96--98\% busy
for both llama.cpp and our engine, which sounds as if the roofline were
reached; it is not, because a kernel that is running is not necessarily a
kernel that is streaming at full rate. And a 2~ms cost per token in the CPU
sampler, one fifteenth of the step, is invisible to every GPU-side tool. Our
first contribution is an instrument that makes each of these visible: GPU
timestamps of the command buffer for each stage, a CPU split of the
inter-token path into forward, sampling and emission, and reference logits
from llama.cpp at chosen decode steps, so that every change is checked where
decode actually runs (\S\ref{sec:method}).

With that instrument we add the model to \ds{}, an open-source
model-specific engine in C and Metal, and pull three levers, each behind a
switch so the final build can reproduce any subset (\S\ref{sec:opt}): the
bytes per step and how fast they move (quantization format and matvec inner
loop); the number and shape of dispatches (a layer's four side projections
in one launch, the SwiGLU gate and up in one kernel, each residual add fused
into the norm that consumes it, and split-KV attention scaled to the
context); and the CPU path between tokens. With the six GPU switches off the
step takes 35.0~ms (generation-loop definition, \S\ref{sec:method}); with
everything on, 30.8~ms, or 30.6~ms forward-only, so the estimated streaming
reference is 79\% of the step.

Four findings are, we think, more useful than the speedup.
\begin{itemize}
\item \textbf{At 27B scale, dispatch count is a first-order term.} The
  initial graph issued about 1,070 dispatches per step; at a few
  microseconds of ramp and drain each, that is as much time as the
  recurrence, the attention and every norm together. The fusions bring it to
  about 620, and the fused gate/up kernel alone is worth 2.1~ms leave-one-out
  (\S\ref{sec:anatomy}, Figure~\ref{fig:ablation}).
\item \textbf{The Q4\_K matvecs are limited by activation traffic, not
  occupancy.} Spreading a reduction over more threads did nothing for the
  wide projections; reading the activation once per four rows instead of
  two, and reading it as vectors, did. The best Q4\_K kernel ends at
  616~GB/s effective against 670 for the Q8\_0 head, and the difference is
  dequantization work (\S\ref{sec:opt}, \S\ref{sec:negative}).
\item \textbf{Format and fusion are not additive.} With simple kernels the
  cheaper Q4\_0 block format is worth 16\% in llama.cpp and 8\% in \ds{};
  with the fused kernels it is worth 2--3\%, because the largest projection
  then streams at the same effective rate in both formats, while Q4\_0 costs
  about 4\% in perplexity. Which lever matters depends on how far the
  kernels already are from the streaming reference (\S\ref{sec:q40}). MLX,
  a general framework on its own affine 4-bit conversion, reaches a step
  time within about 1~ms of ours.
\item \textbf{The CPU is on the critical path.} The 2~ms sampler cost was an
  \texttt{isfinite} call left as a library function by \texttt{-ffast-math};
  the first fix was folded away by the same flags and broke NaN handling.
  The rewritten sampler costs 0.41~ms, and llama.cpp's own full-vocabulary
  top-$p$ sampler 1.2~ms, per token (\S\ref{sec:cpu}). Both facts are
  general to inference code built that way.
\end{itemize}

Our contributions are:
\begin{enumerate}
\item \textbf{A measurement method for Metal decode} with matched timing
  definitions across engines, per-stage GPU spans, a CPU inter-token split
  and a correctness protocol at chosen decode steps (\S\ref{sec:method},
  \S\ref{sec:correctness}).
\item \textbf{Qwen3.8-27B support and a set of decode optimizations}, each
  behind a switch and each measured in isolation (\S\ref{sec:opt},
  Figure~\ref{fig:ablation}). The switches account for 12\% of the step
  within one engine and weight file; the remaining difference to llama.cpp
  is a comparison of complete engines that we do not decompose.
\item \textbf{A controlled quantization-format experiment}
  (\S\ref{sec:q40}) with the same source checkpoint, importance matrix and
  output head in Q4\_0 and Q4\_K, in two engines and at two kernel-fusion
  levels, with the quality cost measured alongside.
\item \textbf{The CPU path as a measured term} (\S\ref{sec:cpu}), including
  the sampler bug, its mechanism and its cost in both engines.
\item \textbf{Negative results with mechanisms} (\S\ref{sec:negative}), a
  profile of a mixture-of-experts model on the same instrument, and the
  code, switches, logs and scripts (Appendix~\ref{sec:repro}).
\end{enumerate}

\ds{} (DwarfStar) is by Salvatore Sanfilippo and contributors~\cite{ds4}
(\upstreamurl{}). It implements a handful of architectures as hand-written
Metal schedules rather than interpreting a generic GGUF computation graph; by
``model-specific'' we mean that the per-token dispatch list is written for the
model, so fusions that depend on the model or the session are local changes.
Our work adds Qwen3.8-27B, including its Gated DeltaNet and gated-attention
kernels, and the decode paths and measurements described here; the engine's
existing design is part of what we measure. The branches, scripts and logs
are at \branchurl{}.

\section{Background}
\label{sec:background}

\subsection{Platform and setup}
The M2~Ultra CPU and GPU share an LPDDR5 memory pool. Metal compiles
kernels at runtime and executes them from command buffers; a compute encoder
holds many dispatches, which execute in order with memory ordering. There is
no host-to-device copy, but the CPU and the GPU share bandwidth, and CPU work
between two tokens is on the critical path.

All measurements are on a Mac Studio with an M2~Ultra (24 CPU cores, 60 GPU
cores, 192~GB LPDDR5, 800~GB/s nominal), macOS 26.1, Apple clang 17.0.0
(clang-1700.4.4.1). Baselines are llama.cpp at commit
\texttt{6d9c82ea2bb34e277c0664b8dd3434bfb4dcfb27} (2026-09-09) built with its
Metal backend~\cite{llamacpp}, and mlx-lm 0.31.3 on mlx 0.32.2~\cite{mlxlm}.
The GGUF engines read the same files from the Unsloth release (revision
\texttt{4ca7207}~\cite{unslothdynamic}); MLX uses the community 4-bit
conversion (revision \texttt{3e6447f}) of the same checkpoint (revision
\texttt{1d4bf0f}~\cite{qwen35}). Appendix~\ref{sec:repro} lists file hashes.

\subsection{Model}
Qwen3.8-27B (GGUF architecture \texttt{qwen35}) has 64 decoder layers plus
one auxiliary multi-token-prediction block that ordinary decode does not
execute; the GGUF therefore has 65 blocks, and the byte accounting below
covers the 64 decoder layers, the output norm and head, and one row of the
token embedding. In three layers out of four the token mixer is Gated
DeltaNet~\cite{yang2025gateddeltanet}: one fused projection produces $q$ and
$k$ (16 heads of 128) and $v$ (48 heads of 128), which pass through a causal
depthwise convolution of width 4 followed by SiLU; $q$ and $k$ are
L2-normalized per head and $q$ is scaled by $1/\sqrt{128}$; value head $h$
uses query/key head $h \bmod 16$; each value head keeps a $128\times128$
recurrent state updated by the delta rule with a scalar decay
$\exp(A \cdot \mathrm{softplus}(\alpha + b))$, where $A = -\exp(A_{\log})$
is a per-head parameter, $b$ a per-head bias and $\alpha$ comes from a
48-wide projection, and a write strength $\sigma(\beta)$ from a second
48-wide projection; the output is RMS-normalized per head and gated by
$\mathrm{SiLU}(z)$ from a 6144-wide projection. Every fourth layer is gated
grouped-query attention: 24 query heads of dimension 256 with 4 KV heads,
per-head RMSNorm on $q$ and $k$, NEOX RoPE on the first 64 dimensions, and
the output multiplied by a sigmoid gate projected alongside $q$. All layers
have a SwiGLU FFN of hidden size 17408; the width is 5120 and the vocabulary
has 248,320 entries. Table~\ref{tab:bytes} gives the bytes a decode step
reads.

\subsection{Streaming bound}
\label{sec:roofline}
At 15.06~GB per step the nominal 800~GB/s bound is 18.8~ms (53~\tps{}). A
more useful reference applies the fastest rate we measure for each format to
its bytes: the Q8\_0 output-head matvec moves 1.35~GB in 2.01~ms (670~GB/s),
and the fastest Q4\_K kernel, the fused gate/up projection, moves 100.3~MB in
162.9~$\mu$s (616~GB/s). Then
\[
T_{\text{weights}} \approx \frac{13.71\,\text{GB}}{616\,\text{GB/s}} + \frac{1.35\,\text{GB}}{670\,\text{GB/s}} \approx 24.3\ \text{ms},
\]
which we call the estimated weight-streaming bound. It assumes every matrix
shape streams at the best measured rate for its format and excludes work
outside the matvecs. Because the rates come from complete kernels, they
already include dequantization and kernel overhead. The estimate is an
empirical reference, rather than a hardware lower bound or a partition of
measured execution time. Throughout, ``utilization'' of this reference means
$24.3$~ms divided by the measured step time; it is not a measurement of DRAM
bandwidth utilization.

\label{sec:method}

\paragraph{Timing definitions.}
Engines count differently: a 64-token run performs 63 decode forwards, the
first token being sampled from the prefill logits, and llama.cpp's
\emph{eval time} excludes sampling while a generation-loop clock includes it.
We therefore report milliseconds per decode forward under two explicit
definitions (Figure~\ref{fig:timeline}), averaging over all 63 forwards of a
run in both engines. Headline numbers are means over five runs (three for
llama.cpp's default-sampler column) on an otherwise idle GPU with the model
file in the page cache; standard deviations are in the result set.

\paragraph{Per-stage GPU spans.}
\ds{} can close and reopen its command buffer at named stage boundaries inside
a layer under an environment switch. We time each stage with the command
buffer's \texttt{GPUStartTime} and \texttt{GPUEndTime}. Timing the same
boundaries with the CPU clock includes a synchronization of about 0.16~ms per
boundary, which is larger than the recurrence, the attention or any norm.
Isolating stages costs wall-clock time (the instrumented run decodes at
8.7~\tps{}) but the GPU spans themselves are little affected: their sum,
31.1~ms, is within 2\% of the uninstrumented forward (30.6~ms). We use the
profile for ranking and for deltas.

\paragraph{System traces.}
Metal System Trace (\texttt{xctrace}) records GPU busy intervals and
command-buffer submissions process-wide; from it we take GPU busy fraction and
CPU encode time per token, for \ds{} and llama.cpp on the same prompt.

\paragraph{Reference logits.}
A small program on the llama.cpp API prefills a prompt, greedy-decodes, and
writes the full logit vector at step $k$, where step 0 is the prefill output
and step $k$ is the output after feeding back $k$ generated tokens; \ds{}
writes the same under a switch. We report mean and maximum absolute
difference over the 248,320 entries, the KL divergence of the softmax
distributions, and argmax agreement, at steps 0, 4, 16, 40 and 63 on a
20-token prompt, at steps 0, 4 and 63 on a 1,439-token prompt, and at step 4
on an 8,590-token prompt. With greedy decoding on both sides the histories
are identical up to $k$ only while the argmax agreed at every earlier step,
so we also compare the 64-token greedy outputs directly and report a step
only when the histories still agree.

\paragraph{The large matvecs are near, not at, the bound.}
The FFN gate/up pair moves 100.3~MB per layer. As two ggml-style matvecs plus
a SwiGLU kernel its effective rate is 513~GB/s; fused and vectorized
(\S\ref{sec:opt}), 616~GB/s. The 5120-output projections (FFN down, attention
and DeltaNet output) run at 390--450~GB/s with the ggml-style kernel. The
Q8\_0 output head reaches 670~GB/s on the same memory system. Effective rate
is bytes over kernel time, not a measurement of DRAM traffic; the difference
between formats is consistent with the ALU cost of unpacking Q4\_K's 6-bit
sub-block scales and minimums. Section~\ref{sec:q40} compares the formats
under different kernel configurations to examine their interaction.

\paragraph{Dispatch count matters at this scale.}
The initial model implementation issued about 1,070 dispatches per step (16 per
DeltaNet layer, 19 per attention layer, plus embedding and head). At a few
microseconds of ramp and drain each, that is 3--5~ms, as much as the
recurrence, the attention and all norms together. The final graph issues about
620.

\paragraph{GPU busy is not GPU useful.}
On the mixed-recipe UD-Q4\_K\_M file, the system trace shows \ds{} at 98.3\%
GPU busy against 95.6\% for llama.cpp, with about 1~ms of CPU encode time per
token against 4.9~ms. Both engines keep the GPU occupied; the gap to the bound
is mostly inside kernels, not between them, which is why the work below is
mostly about kernel shape and fusion.

\section{Optimizations by lever}
\label{sec:opt}

Six optimizations have runtime switches (Appendix~\ref{sec:repro} lists
them); Figure~\ref{fig:ablation} and Table~\ref{tab:ablation} give their
leave-one-out effects around the optimized build, in milliseconds per decode
forward. Leave-one-out effects around the final build need not equal
standalone gains from the original build, and several switches remove the
same dispatch overhead, so they do not sum to the all-off difference.

\subsection{Bytes: how fast a byte moves}
The format fixes the byte count; the kernel decides the effective rate. Two
changes to the Q4\_K inner loop were worth 9.6\% on the fused gate/up kernel
(178.6 to 162.9~$\mu$s per layer): staging the 32 activation values a lane
needs as eight \texttt{float4} loads instead of 32 scalar loads (the
activation pointer's alignment is not provable to the compiler, so it does not
vectorize the loads itself), and loading each lane's two 8-byte nibble runs as
\texttt{uint2} instead of four \texttt{uint16}. Amortizing one activation
staging over four rows per simdgroup instead of two helped the 10240- and
12288-output projections in the stage profile and hurt the 5120-output ones,
so the row count is chosen per shape; end to end the difference is within
noise. A K-split variant, which spreads one row's reduction over the
simdgroups of a threadgroup and combines through threadgroup memory, helps
only the long-row FFN down projection (17408 inputs: 112 to 95~$\mu$s) and is
used only there.

\subsection{Dispatches: fewer and better shaped}
\paragraph{Multi-weight matvec.} A DeltaNet layer's four side projections
($qkv$, $z$, $\alpha$, $\beta$) share one activation and one input width. One
kernel with up to four weight segments, dispatched as a single grid whose
threadgroup ranges map to segments, writes the outputs back to back into the
existing batch buffer; the convolution and recurrence read $z$, $\alpha$ and
$\beta$ through views. The same kernel issues $q|$gate, $k$ and $v$ of an
attention layer. Four launches become one, and the 48-output $\alpha$ and
$\beta$ heads no longer each pay a dispatch.
\paragraph{Fused gate/up SwiGLU.} One kernel streams the gate and up weights
against one staged activation and writes $\mathrm{SiLU}(g)\cdot u$; the
elementwise pass disappears and the activation is read once per four rows
instead of once per two.
\paragraph{Residual add fused into the next norm.} Each residual add is fused
with the RMSNorm that consumes its result, so a layer's FFN epilogue produces
the next layer's attention-norm input; two adds and two norms per layer become
two kernels.
\paragraph{Single attention prologue.} Per-head RMSNorm plus RoPE for the
query heads, the same for the key heads into the f16 K cache, and the $V$
store are one grid with three kinds of threadgroup instead of three launches
(this one has no switch).
\paragraph{Context-scaled split-KV.} The split-KV decode attention kernel
adapted from ggml partitions the keys over 32 workgroups and reduces their
partials in a second kernel. At a 20-token context 31 workgroups are idle and
the reduce dominates. Scaling the workgroup count with the context length,
and letting a single workgroup write its normalized output directly, cuts the
attention stage from 106 to 60~$\mu$s per layer; the shared reduce kernel had
silently assumed 32 workgroups and was made correct for fewer.

\subsection{The CPU path between tokens}
\label{sec:cpu}
Sampling settings first, since they decide what the sampler has to do. The
model's generation configuration specifies temperature 1.0, top-$p$ 0.95 and
top-$k$ 20; llama.cpp reads these from the file's metadata and its default
chain applied top-$k$ 20 and min-$p$ 0.05 in our runs. \ds{}'s Qwen defaults
are temperature 1.0 and top-$p$ 0.95 with no top-$k$ and no min-$p$, so its
sampler scans the full 248,320-entry distribution every token; this is the
configuration studied here, and for comparison we also ran llama.cpp with
the same settings (\texttt{--top-k 0 --min-p 0}).

Under those settings the CLI spent 2.2~ms per token in \ds{}'s sampler
against 30.5~ms in the forward. The cost was not the softmax or the sort but
\texttt{isfinite()} on each logit, twice per token: the engine is compiled
with \texttt{-ffast-math}, under which Apple clang 17 leaves \texttt{isfinite}
as a call to \texttt{\_\_\_isfinitef} and the scan runs scalar at about 4~ns
per element. A first replacement, an exponent-bit test on the float value,
was folded to ``always finite'' by the optimizer under the same flags,
admitted NaN and $-\infty$ logits, and failed 1,459 unit tests; the working
version tests the bits as loaded from memory, which the optimizer does not
classify. The finite test alone did not recover the time; the gain came from
rewriting the max scan and the top-$p$ pass branch-free and block-wise so
they vectorize, with a degree-5 fit of $2^x$ (relative error under $2\times
10^{-6}$) for the tail mass that cannot enter the 512-entry candidate heap,
and a lowering-cutoff fallback instead of a full-vocabulary sort. The sampler
now costs 0.41~ms per token. The flags cut both ways: the same sampler built
with \texttt{-fno-finite-math-only}, which inlines \texttt{isfinite}, costs
0.74~ms, because the vectorized scans lose the fast-math assumptions. For
scale, llama.cpp's sampler costs 0.13~ms per token with its default top-$k$
20 chain and 1.21~ms with the full-vocabulary top-$p$ settings. Two lessons are general: measure the inter-token gap on the
CPU, and treat fast-math flags as part of the numerical contract of code that
handles non-finite values. Whether other compilers or SDK versions behave the
same way we have not checked.

\subsection{Quality of the files}
We measure the quantization quality of the GGUF files with llama.cpp; the
logit comparisons above separately establish \ds{}'s numerical agreement
with that implementation on the tested prompts and steps, and do not by
themselves prove that quality is engine-independent along long generations.

because all files score the same chunks we report the paired relative
perplexity change with a chunk-level standard error, which is the

\label{sec:eval}

\subsection{Decode step time}
Table~\ref{tab:tps} gives the headline comparison under both timing
definitions. On pure Q4\_K, \ds{} takes 30.6~ms per decode forward against
42.3 for llama.cpp, an approximately 28\% shorter step; the estimated streaming bound of
24.3~ms is 79\% of it. The step is about 26~ms of weight-carrying matvecs at

per token in \ds{} and 0.1~ms (default chain) or 1.2~ms (full-vocabulary

\subsection{Context length and the MLX baseline}
Figure~\ref{fig:context} sweeps the prompt from 1.4k to 33k tokens (values in
Table~\ref{tab:context}, appendix; three runs each). \ds{}'s step grows from
31.4 to 38.1~ms and llama.cpp's from 42.5 to 49.4. The DeltaNet stages vary
little between the short- and 8.6k-context profiles
(Table~\ref{tab:stages}). The sixteen attention layers read a K/V cache
of 64~KiB per position summed over those layers; their attention stage,
including split-KV reduction, grows from 0.96 to 3.36~ms per step between
20 and 8,590 tokens. Prefill throughput is the same in \ds{} and llama.cpp within 4\% at
every length: prefill is a matrix--matrix workload on comparable
dequantize-and-multiply kernels.

MLX is a practical baseline rather than a controlled one. Its community
conversion stores the layers in 4-bit affine format (a 16-bit scale and bias
per group of 64; 4.5 bits per weight, the same as Q4\_K) but also the output
head, at 715~MB against our Q8\_0 head's 1.35~GB, about 1~ms per step at
these rates; mlx-lm reports only the generation loop; and the model code is
Python over the framework's primitives. On the same 20-token prompt its loop
takes 29.8~ms per forward, comparable to \ds{}'s 30.7, and it tracks \ds{}
across context lengths (30.4 to 37.1~ms, within about 1~ms of \ds{} at every
length) with prefill 13--18\% slower. The comparison shows
that a general framework on a cheaper format reaches a similar step time; it
does not isolate the format, which is what \S\ref{sec:q40} does.

\subsection{Quantization format and kernel organization}
\label{sec:q40}
To separate the quantization format from everything else we built two files
from the same Q8\_0 source with the same importance matrix and the same
Q8\_0 output head: pure Q4\_K and pure Q4\_0, the same bit budget (16.0~GB on

values. Q4\_0 stores one 16-bit scale per 32 weights and dequantizes with one
multiply-add per weight; Q4\_K packs 6-bit sub-block scales and minimums into

matvec into \ds{} and then the fused gate/up and multi-weight kernels;

With the baseline kernels, Q4\_0 shortens the step by 16\% in llama.cpp
and 8\% in \ds{}. In \ds{}, its gate/up pair takes 171~$\mu$s per layer
against 196 for Q4\_K. With the fused kernels, the two formats take 30.0
and 30.8~ms, respectively, a difference of approximately 2.5\%. The fused
gate/up kernel takes 166~$\mu$s in Q4\_0 and 163 in Q4\_K, both about
610~GB/s effective. Thus, the simpler format provides no measured advantage
on the largest projection under these fused implementations.

The remaining differences depend on matrix shape and kernel choice. Q4\_0
is faster on the narrower projections (84 versus 94~$\mu$s for the
DeltaNet projections, and 75 versus 82 for attention) but slower on FFN down
(103 versus 95~$\mu$s), where only Q4\_K uses a K-split kernel. These
results support evaluating the format and its implementation together; they
do not isolate dequantization instruction cost from the other kernel
differences. The smaller latency advantage after fusion is accompanied by
approximately 4\% higher perplexity for Q4\_0 on the evaluated chunks.

\subsection{A second family: mixture of experts}

\section{What did not work}
\label{sec:negative}
\paragraph{K-split on wide matrices (measured).} Splitting the reduction
across the simdgroups of a threadgroup multiplies the thread count for a
fixed number of output rows. It helped only the long-row FFN down projection
and was neutral or slightly worse on the 10240- and 12288-output projections.
This is consistent with activation re-reads per row, not occupancy, being the
limiter on those shapes, since rows per simdgroup was the parameter that
moved them; a change of rows per simdgroup alters several things at once,
and we did not isolate the mechanism further.
\paragraph{Output gate fused into the attention reduce (measured).} A copy of
the split-KV reduce that multiplies by $\sigma(\text{gate})$ before its single
store was consistently 20~$\mu$s per layer slower than the shared reduce
followed by a trivial elementwise gate kernel, even with the gate arithmetic
removed. The copy specializes its loops on function constants where the shared
kernel takes them as runtime arguments; we did not confirm that this is the
cause, and dropped the fusion.
\paragraph{Convolution folded into the recurrence (rejected by estimate, not
measured).} In the proposed design each of the 1,536 recurrence
threadgroups would recompute the causal convolution for the 256 $q$/$k$
channels of its head; with 16 distinct $q$/$k$ heads shared by 48 value
heads, each unique channel would be recomputed 96 times, and the convolution
state re-read as often. We judged the redundant work larger than the one
dispatch it would save and did not implement it.

\section{Discussion}
\label{sec:discussion}
\paragraph{What the levers are worth here.} Of the 11.6~ms between
llama.cpp's forward and \ds{}'s, 4.2~ms are the switches of this paper,
measured within one engine and one weight file; the rest is a comparison of
complete engines, which the profiles of \S\ref{sec:anatomy} attribute to
dispatch count and CPU encoding but which we did not ablate across engines.
The controlled experiment puts the format lever at 0.8~ms once the kernels
are fused and at 2.8--6.9~ms when they are not, so the return from changing
the format depends on the kernels it meets. GPU timestamps, CPU critical-path
effects and context-dependent attention partitioning are not unique to
unified memory; what is specific to this setting is that at 27B scale on one
GPU, per-dispatch cost and CPU gaps are each a few percent of the step and
add up, and that a slow sampler is invisible to every GPU-side tool.
\paragraph{Hand-written schedules against frameworks.} \ds{} implements each
family as a hand-written Metal schedule; the cost is that each new family is a
port, the benefit is that fusions which depend on the model or the session
(batching a layer's side projections, scaling split-KV work to the context)
are local changes with measured effects. llama.cpp and MLX both fuse some
operators; we have not audited which, and the MLX result shows that a cheaper
format on a general framework reaches a similar step time.
\paragraph{What is left.} The optimized forward is 6.3~ms above the 24.3~ms
streaming reference. Because the reference assigns the best observed rate to
every matrix shape, that difference includes the slower matvecs as well as
the latency-bound recurrence, the attention path, per-dispatch ramp and host
work, and the measurements do not partition it exactly; \S\ref{sec:q40}
indicates that dequantization is a small term once the large matvecs are
fused. The model ships a multi-token prediction block, so several candidate
positions could be verified per weight pass; the benefit depends on
acceptance rates, drafting cost and verifying the recurrent state, and we
have not measured it.

\section{Related work}
\paragraph{Local inference runtimes.} llama.cpp and ggml~\cite{llamacpp,ggml}
are the reference for consumer-hardware inference; \ds{}'s Q4\_K and Q4\_0
matvecs and its split-KV decode attention are ports and adaptations of theirs,
and the fused kernels of \S\ref{sec:opt} are new. MLX~\cite{mlx} is Apple's
array framework; mlx-lm~\cite{mlxlm} implements the Gated DeltaNet families.
\paragraph{Roofline and phase analyses.} FlashAttention~\cite{dao2022flashattention}
made attention IO-aware for training and prefill; Flash-Decoding~\cite{dao2023flashdecoding}
partitions decode attention along the key sequence, which is the design the
split-KV kernel here follows; disaggregated serving~\cite{patel2024splitwise,zhong2024distserve}
separates the prefill and decode phases at the cluster level. These target
discrete GPUs and batched serving; we measure single-stream decode where the
CPU shares the memory system.
\paragraph{Hybrid linear-attention models.} Gated
DeltaNet~\cite{yang2025gateddeltanet} and the Qwen3-Next and Qwen3.5
families~\cite{qwen3next,qwen35} interleave linear-attention layers with a
minority of softmax-attention layers; the reference CUDA kernels~\cite{yang2024fla}
cannot be used on Metal, and the decode recurrence here is a direct
implementation of the delta rule.
\paragraph{Quantization formats.} Weight-only quantization
methods~\cite{frantar2023gptq,lin2024awq}, the k-quant block
formats~\cite{kquants}, importance-matrix calibration~\cite{imatrix} and
mixed-recipe files~\cite{unslothdynamic} trade bytes for dequantization work;
\S\ref{sec:q40} measures that trade on an Apple GPU.
\paragraph{Speculative and multi-token decoding.} Verifying several tokens per
weight pass~\cite{leviathan2023fast,chen2023accelerating,cai2024medusa,li2024eagle}
is the standard route past the streaming bound; the model used here ships a
multi-token prediction block~\cite{gloeckle2024mtp,deepseekv3}.

\section{Limitations}
All results are from one machine, an M2~Ultra with a 60-core GPU; achieved
rates and the balance between levers will differ on other generations (the
M5 family adds GPU matrix units that change the prefill regime), and a device
sweep is the obvious extension. The decomposition is for one dense hybrid
family; the MoE result is a step time and a profile, not an ablation. The
per-stage profiler perturbs what it measures by isolating stages, so we use
it for rankings and deltas. Effective bandwidths are bytes over kernel time,
not counter measurements; the mechanisms proposed for the kernel results are
consistent with the data but were not isolated with microbenchmarks. The
correctness checks are spot checks at eight points; perplexity is on forty
chunks of one corpus; the sampler finding depends on the compiler and flags.

\section{Conclusion}
A decode step on Apple silicon is not simply bandwidth bound at the 27B
scale: matvec kernel shape, dispatch count and CPU work between tokens each
cost milliseconds, and each needs its own measurement. GPU timestamps per
stage and a CPU inter-token split turned each optimization into a targeted
change with a measured effect, and the switches make the account auditable:
12\% of the step within one engine and weight file, and a sampler fix of
1.8~ms per token that no GPU-side tool could have found. The controlled
format experiment shows where one lever stops and another starts: the
cheaper block format is worth 8--16\% against simple kernels and 2--3\%
against fused ones, so a quantization format has to be judged together with
the kernels that read it.

\subsection{Downstream check}
\label{sec:downstream}
As a coarse check on reasoning tasks we ran \ds{}'s built-in evaluation
harness on its first ten questions (drawn from GPQA Diamond, SuperGPQA and
AIME 2025) with thinking enabled, greedy decoding and a 2,500-token reply
budget. The harness forces the thinking block closed near the budget and
extracts an answer from what follows, so a cut-off answer can still be
correct. Pure Q4\_K scored 8/10 (3 cut off), pure Q4\_0 7/10 (3), Q8\_0
7/10 (4): within one question of each other, which is the resolution of ten
items, and not evidence of a ranking.
